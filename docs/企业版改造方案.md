# 星火工作台 · 团队/企业版改造方案

> 版本：v1.0（2026-10-25） · 基于当前代码全量走查（server.js / src/ 19 个模块 / public/ 4 页面 + 3 静态资源 / data/db.json）
> 原则：**最小侵入**——复用 Express + 零依赖 + db.json 的现有结构，不做框架迁移、不做数据库更换、不做整体重写。

---

## 第一部分 · 现状评估

### 1.1 技术栈与架构现状

| 层 | 现状 | 评价 |
| --- | --- | --- |
| 运行时 | Node.js ≥ 18 + Express 4（`package.json` 唯一依赖） | 轻、可控；无框架升级负担 |
| 前端 | 零构建原生 HTML/CSS/JS：`index.html`（工作台）、`login.html`（访客登录）、`admin.html` + `admin-login.html`（后台），`app.js`(812 行) / `admin.js`(753 行) / `style.css`(446 行) | 改完刷新即生效，适合小团队维护；无组件化、无构建校验 |
| 数据层 | `src/db.js`：单文件 `data/db.json`，启动时读入内存缓存，**每次写操作全量同步 `writeFileSync` 整个文件** | 备份/迁移就是拷一个文件（优点）；但有写放大、无原子写、无并发保护（见 1.5） |
| 认证 | `src/adminAuth.js`（312 行，零依赖 node:crypto）：scrypt 加盐哈希 + HMAC-SHA256 签名 Cookie（`admin_token = v1.<过期时间>.<签名>`，HttpOnly / SameSite=Lax / 12h）；`wb_token` 访客会话复用同一 `sessionSecret` | 设计干净、注释完备；但**会话令牌只签过期时间、不签身份**，无法支撑多用户 RBAC |
| 进程 | 单进程；`asyncHandler` + `uncaughtException` / `unhandledRejection` 兜底 | 单请求出错不打挂服务，这一点已被历史故障验证过 |

### 1.2 数据模型现状（data/db.json）

```
{
  configs: [...],       // API 配置：30+ 字段（key/model/参数/调度优先级/TTI），apiKey 明文存储
  logs: [...],          // 运行日志，内存上限 5000 条，超出丢最旧；含完整请求/响应体
  conversations: [...], // 会话 + 消息；消息图片只存 /uploads URL，发送前转 base64 内联
  settings: {
    autoSwitch, cooldownSec,
    sessionSecret,                 // 会话签名密钥
    adminPasswordHash,             // 唯一管理员密码哈希
    workbenchPasswordHash,         // 唯一访客密码哈希
    workbenchAuthEnabled           // 访客开关
  }
}
```

当前库内实际数据：1 条配置、36 条日志、1 个空会话（含少量历史乱码日志，见技术债 T12）。

### 1.3 现有能力清单（可直接复用的资产）

**前台工作台**
- 多会话管理（新建/切换/删除/清空，自动命名）
- 多 API 配置下拉切换；多配置调度（优先级 + 失败冷却 + 自动切换，`scheduler.js`）
- 文本对话 / SSE 流式透传 / 响应明细（耗时、token、缓存命中、推理 token、工具调用）
- 图片粘贴上传四通道（Ctrl+V / 右键 / 拖拽 / 选择），魔数校验 + 尺寸解析 + 落盘
- 联网搜索开关、深度思考/强度/系统提示参数工具栏（localStorage 记忆）

**后台管理（单密码登录）**
- API 配置 CRUD、连通性测试、参数面板、TTI 设置
- 运行日志（分页 + 状态筛选 + 详情）
- 云中心延时探测
- 记忆管理（关键字搜索 / 统计 / 管理员备注 / JSON·Markdown 导出 / 删除）
- 访客密码开关、修改密码

**安全机制（已具备，企业版可继承）**
- scrypt 哈希 + `timingSafeEqual` 常量时间比对
- 登录失败限流：同 IP 连续 5 次错误锁 60 秒（`adminAuth.failMap`）
- 改密轮换 `sessionSecret` → 全部会话失效
- 上传白名单（魔数 + 尺寸 50~6000 + 单张 8MB + 目录穿越防护）
- API Key 前端脱敏（`maskKey`）、日志 data URI 脱敏（`redactForLog`）

| --- | --- | --- |

### 1.5 技术债与风险点（按严重度分级）

| # | 级别 | 问题 | 证据 / 影响 |
| --- | --- | --- | --- |
| T1 | **P0 阻塞** | 无用户体系，会话令牌不含身份（`v1.<exp>.<sig>` 只签过期时间） | 所有 RBAC、数据隔离、操作留痕都无从落地；这是企业版的第一个地基缺口 |
| T2 | **P0 阻塞** | 「改密轮换 `sessionSecret`」是全局核弹 | 企业场景任何人改密会把全公司踢下线；需要按用户失效 |
| T3 | P1 高 | `db.js` 每次写操作**全量同步写回整个 db.json**，无原子写、无并发保护 | 日志/会话/用户增长后写放大；进程崩溃可能写坏文件（无 tmp+rename）；外部改 db.json 会被内存缓存覆盖（历史踩坑：`2026-10-25.md` 有记录） |
| T4 | P1 高 | 日志记录**完整请求/响应体（含用户输入全文）**，且登录即可看全部 | 多员工场景是隐私/合规问题；企业版必须按角色过滤 |
| T5 | P1 高 | API Key **明文**存 `configs[].apiKey` | 文件被拷走即泄露；db.json 已在 .gitignore，但备份/分享仍裸奔 |
| T6 | P1 高 | 无审计日志 | 配置误改、数据被删无法追溯；企业版底线能力 |
| T7 | P2 中 | 登录限流是内存 Map：IP 单维度、重启清零 | 撞库单账号无防护；重启后锁失效 |
| T8 | P2 中 | `GET /api/configs` 免登录返回全部配置结构 | Key 已脱敏，但 baseUrl/模型/命名对未登录者可见 |
| T9 | P2 中 | 无响应式（`.workbench{display:flex}` 固定侧栏、后台 12 列表格） | 手机/平板不可用；竞品标配 |
| T10 | P2 中 | 密码策略弱（≥4 位即可）、无用户名概念 | 企业版需 ≥8 位 + 复杂度 + 字段校验 |
| T11 | P2 中 | 日志 5000 条上限直接丢最旧 | 团队用量下日志留存不足，且无归档 |
| T12 | P3 低 | db.json 历史脏数据（乱码日志）、TTI 半成品、无测试 | 迁移时做一次数据清洗；测试随改造补 |
| T13 | P3 低 | 单进程单机部署（ECS + 小皮面板已验证） | 团队规模 <50 人可接受；明确不做多实例/集群 |

## 第二部分 · 改造方案

### 2.0 总体设计（一张图看懂目标形态）

```
                 ┌────────────────────────────────────────────┐
   员工浏览器 →  │  Express 单进程（保持零新增运行时依赖）      │
                 │                                            │
   登录页 ─────→ │  /api/auth/*        （免登录：login/logout）│
                 │  /api/admin/*       （requireTeamUser +    │
   后台   ─────→ │                     requireRole 按路由分级）│
                 │  /api/configs       （GET 登录可用，写=Admin+）│
   工作台 ─────→ │  /api/chat /conversations /upload /image   │
                 │                     （登录可用，数据按角色隔离）│
                 │                                            │
                 │  userService   账号 CRUD / 登录校验 / 停用   │
                 │  auditService  操作留痕（环形缓冲存 db.json） │
                 │  db.js         users / auditLogs 新集合     │
                 └────────────────────────────────────────────┘
```

**核心设计决策（3 个，先说清楚）：**

1. **会话令牌升级为 v2：`v2.<userId>.<role>.<exp>.<sig>`**
   `sig = HMAC(sessionSecret, "<userId>|<role>|<exp>|<passwordUpdatedAt>")`。
   签名里带 `passwordUpdatedAt`：某人改密后**只有他的会话失效**（修 T2），其余人无感。
   校验时用内存 users 表确认 `status=active` → 停用账号**最多延迟一个请求周期即失效**（停用语义即时）。
   保留 v1 只读兼容 7 天（映射为 owner 身份），到期移除，平滑过渡。

2. **角色模型四级（最小可用集）：**
   `owner`（超管，唯一，可转让）> `admin`（配置+成员+日志，不可看他人私聊除非策略允许）> `member`（用工作台，看自己数据）> `viewer`（只读看板）。
   权限矩阵见 2.3。

3. **数据归属打标：** `conversations` 与 `logs` 增加 `ownerId` 字段；历史数据迁移时统一标记为 `owner`。
   「停用账号」= `status=disabled`，**不删任何数据**（userId 永远留在数据上，满足「历史数据完整保留」）。

### 2.1 阶段 0（P0）：员工账号体系 —— 地基

> 目标：用户名/密码注册登录、字段校验、密码安全存储、会话管理、登录失败与异常处理。本阶段不碰任何业务逻辑，风险最低、价值最大（解锁后续一切）。

**新增文件（3 个，均为小文件）**

| 文件 | 职责 |
| --- | --- |
| `src/userService.js` | 用户 CRUD、登录校验（用户名唯一、scrypt 哈希复用 adminAuth）、状态检查；预计 ~180 行 |
| `src/routes/auth.js` | `POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me`、`PUT /api/auth/password`（自助改密，只踢自己） |
| `public/team-login.html` | 员工登录页（复用 `.login-card` 样式与 `admin-login.html` 结构，零新 CSS） |

**改造文件（4 个）**

| 文件 | 改动 | 影响范围 |
| --- | --- | --- |
| `src/db.js` | `DEFAULT_DB` 增加 `users: []`、`auditLogs: []`；`load()` 补数组默认值（旧库无需手工迁移） | 全局数据层，纯增量 |
| `src/adminAuth.js` | ① `issueCookie` 升级 v2（签身份+passwordUpdatedAt）；② `hasValidToken` 兼容 v1（7 天）；③ 新增 `requireTeamUser(req,res,next)`（注入 `req.user={id,username,role,displayName}`）；④ 新增 `requireRole(...roles)` 中间件工厂；⑤ 导出 `hashPassword/verifyPassword` 供 userService 复用 | 所有鉴权路径；**这是本阶段唯一需要小心的文件** |
| `server.js` | 挂载 `/api/auth`；`/api/admin` 守卫由 `requireAdminApi` 改为 `requireTeamUser`（旧 owner 密码保留为应急通道，见「迁移」） | 路由挂载区，约 10 行 |
| `public/assets/style.css` | 不改（复用登录页样式） | — |

**数据模型（增量）**

```js
users: [{
  id: "usr_<36进制>",          // db.getNextId('usr')
  username: "zhangsan",        // 3-20 位 [a-z0-9_]，大小写不敏感唯一
  displayName: "张三",
  role: "owner|admin|member|viewer",
  passwordHash: "scrypt$1$...",
  status: "active|disabled",
  mustChangePassword: false,   // 管理员重置密码后置 true，登录后强制改密
  passwordUpdatedAt: "ISO",
  lastLoginAt: "ISO|null",
  createdAt, updatedAt, note
}]
```

**注册/登录/异常处理设计（对应需求 1）**

- 注册：v1 仅「管理员创建账号」（阶段 1 落地）；开放自助注册列为 P3 可选开关（默认关）。
- 字段校验（前后端双重）：用户名 3-20 位 `[a-z0-9_]` 唯一；昵称 1-30 字；密码 **≥8 位且含字母+数字**（替代现有 4 位策略，T10）；确认密码一致。
- 密码存储：scrypt(随机盐, 64B)，格式沿用 `scrypt$1$<salt>$<hash>`，零新增依赖。
- 会话：HttpOnly + SameSite=Lax + 12h（`ADMIN_SESSION_TTL_HOURS` 沿用）；`GET /api/auth/me` 供前端探活。
- 登录失败：① IP 维度 5 次/60s（沿用 failMap）；② **新增用户名维度** 5 次锁 5 分钟（修 T7）；③ 文案统一「用户名或密码错误」（不暴露账号是否存在）；④ `status=disabled` 明确提示「账号已停用，请联系管理员」。
- 异常：所有入口包 `asyncHandler`；登录接口对异常返回 500 JSON 而非裸栈。

**迁移策略（bootstrap 幂等，停服/不停服均可）**

```
db.json 无 users 且有 adminPasswordHash
  → 创建 owner 用户：{ username:'owner', role:'owner', hash 沿用, mustChangePassword:true }
  → 历史 conversations/logs 补 ownerId='owner'（保留 createdBy=null 表示系统）
  → v1 admin_token 会话保留只读兼容 7 天
```

**风险与回滚**

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| 会话格式变更 → 一次性全员重新登录 | 低 | 公告 + v1 兼容 7 天 |
| adminAuth.js 改动波及所有守卫 | 中 | 改动集中、单文件可 diff；旧函数保留不删 |
| 迁移脚本不幂等导致重复建 owner | 低 | `users.find(u=>u.username==='owner')` 判重 |
| 回滚 | — | `git checkout` 代码 + db.json 备份即可完全回退 |

### 2.2 阶段 1（P1）：账号管理 + 权限分级 + 操作留痕

> 目标：管理员可查看员工列表、启用/停用（停用即禁登录、数据保留）、按角色鉴权、关键操作留痕。对应需求 2 与需求 4 的权限分级。

**新增文件（2 个）**

| 文件 | 职责 |
| --- | --- |
| `src/routes/admin-users.js` | `GET/POST /api/admin/users`、`PUT /api/admin/users/:id`（改角色/启停/重置密码）、`DELETE /api/admin/users/:id`（软删=停用，保留数据） |
| `src/routes/audit.js` | `GET /api/admin/audit-logs`（分页 + 按操作人/动作/时间筛选） |

**改造文件**

| 文件 | 改动 |
| --- | --- |
| `src/auditService.js`（新） | `log(actor, action, target, detail, ip)` 写 `auditLogs`；环形缓冲保留最近 2000 条；在 admin.js / config.js / admin-users.js 关键写操作处埋点 |
| `server.js` | 挂载两个新路由；`/api/admin/users`、`/api/admin/audit-logs` 加 `requireRole('owner','admin')` |
| `src/routes/admin.js` | 登录成功/失败埋点；记忆管理删除操作埋点 |
| `src/routes/config.js` | 配置增删改 + 测试埋点 |
| `public/admin.html` | 新增「成员管理」「审计日志」两个 tab + 用户编辑弹层（复用 `.modal` 结构） |
| `public/assets/admin.js` | 用户列表渲染、启停/角色/重置密码交互、审计日志表格；顶栏展示当前登录用户与角色 |

**权限矩阵**

| 操作 | owner | admin | member | viewer |
| --- | --- | --- | --- | --- |
| 使用工作台对话 / 上传图片 | ✅ | ✅ | ✅ | ❌ |
| 查看自己的会话/日志 | ✅ | ✅ | ✅ | — |
| 查看全部会话/日志（记忆管理） | ✅ | ✅ | ❌（仅自己） | ❌ |
| API 配置查看 | ✅ | ✅ | ✅（脱敏） | ✅（只读） |
| API 配置增删改 / 测试 | ✅ | ✅ | ❌ | ❌ |
| 成员管理（增/停用/角色/重置密码） | ✅ | ✅ | ❌ | ❌ |
| 审计日志查看 | ✅ | ✅ | ❌ | ❌ |
| 访客密码开关 / 全局调度设置 | ✅ | ✅ | ❌ | ❌ |

**停用语义（对应需求 2）**

- `PUT /api/admin/users/:id {status:'disabled'}` → 该用户下次请求即 401（token 校验时查 users 表）；
- **不删除 users 记录、不删除其 conversations/logs**；数据上 `ownerId` 永久保留，重新启用后历史数据原样可见；
- 禁止停用自己、禁止停用最后一个 owner；
- 管理员「重置密码」= 生成随机临时密码 + `mustChangePassword=true`，首次登录强制改密。

**风险与回滚**：本阶段新增路由都是增量挂载，不动既有写操作逻辑（只加埋点调用）；回滚 = 摘路由 + 恢复 admin.js/admin.html。中风险点在「token 校验查 users 表」要防 users 为空时的兜底（v1 兼容分支）。

### 2.3 阶段 2（P2）：数据归属、可见范围与数据查看增强

**改造文件**

| `src/routes/config.js` | `GET /api/configs` 从「免登录」改为「登录可用」（修 T8；工作台 app.js 已带 cookie，无感） |

## 第三部分 · 优先级总表与实施顺序

| 序 | 阶段 | 需求映射 | 新增文件 | 改造文件 | 工作量 | 风险 | 依赖 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | **P0 账号体系** | 需求 1 全部 | 3 | db.js / adminAuth.js / server.js | 中 | **中**（adminAuth 是唯一敏感点） | 无 |
| 2 | **P1 账号管理+RBAC+审计** | 需求 2、需求 4 权限分级/留痕 | 3 | server.js / admin.js / config.js / admin.html / admin.js | 中大 | 中 | P0 |

**为什么这个顺序**：账号体系是所有其他能力的地基（没有用户身份，RBAC/留痕/隔离都无从谈起）；P2 的数据隔离只依赖 P0 的身份注入，可与 P1 并行；P3 的响应式完全独立，任何时候可插队。

**建议节奏**：每个阶段独立上线、独立验证、独立可回滚；阶段之间不停服（bootstrap 幂等迁移）。

## 第四部分 · 验收标准

**P0**
- [ ] 新用户可登录/登出；错误密码、不存在用户、停用用户分别返回约定文案
- [ ] 密码 ≥8 位复杂度校验生效；scrypt 哈希落库（无明文）
- [ ] 某用户改密后，其他在线用户会话不受影响
- [ ] IP 5 次/60s + 用户名 5 次/5min 限流生效
- [ ] 旧后台密码迁移为 owner 且强制改密；v1 令牌 7 天内仍放行

**P1**
- [ ] 管理员可见员工列表（用户名/角色/状态/最近登录）
- [ ] 停用后：该账号立即无法登录、API 401；其会话/日志在后台完整可见
- [ ] 四角色权限矩阵逐条验证通过（特别是 member 看不到他人数据）
- [ ] 审计日志可查到：登录成败、用户启停、配置变更、数据删除

**P2**
- [ ] member 登录后台「记忆管理」只能看到自己的会话
- [ ] 概览卡数字与日志聚合一致
- [ ] 日志页支持关键字/模型/时间范围筛选与排序

**P3**
- [ ] 375px 宽度下工作台与后台主要功能可用
- [ ] `db.js` 写坏模拟（kill -9）后 tmp+rename 不丢已提交数据
